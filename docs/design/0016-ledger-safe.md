## Summary

- **Today** main drives the Ledger with hw-app-eth, which builds every APDU. Main builds every Safe transaction and calldata with protocol-kit, and the address and deployment itself from pinned constants (#1066), and reads the Safe's nonce from the first RPC endpoint that answers. The core signs only for vault accounts: a Safe's vault owners and its executor.
- **Ledger (proposed):** main keeps the USB device and relays APDUs. The core builds every APDU from the approved request, checks every answer, and recovers every signature against the account and the digest the user confirmed before anything leaves it. One core-to-main request, `shell.ledger_apdu`, carries one APDU. Main admits only the APDUs that the open operation's row of a closed [grammar](#the-apdu-grammar) allows, and derives every byte of them itself from the request it sent or the approval it recorded, so a faulty core can't put other bytes on the device. hw-app-eth leaves the browser.
- **Typed data on the device ([Q23](#open-questions), decided 2026-11-24):** field by field, as today. The hash-only fallback, which shows the user two hashes and nothing else, stays: only after the device answers `6D00` to the operation's first `E0 1A`, with `fc-evm`'s hashes, and with a warning, on screen before the device asks, that the device shows only hashes.
- **Bounds:** one device operation at a time, 15 s for an APDU the user doesn't confirm, 5 minutes for one they do, a Cancel, and a defined end when the device is unplugged. Today a signature can wait forever, and only the device can end it.
- **Safe ([Q24](#open-questions), decided 2026-11-24 as proposed):** only the Safes Freedom creates today, Safe 1.4.1 on Gnosis. Their deployment addresses and the factory's proxy code are pinned in a new logic crate, `fc-safe`, which computes the address, the deployment, the SafeTx, its hash, the SafeMessage and the `execTransaction` calldata. The Safe's nonce, owners, threshold and setup are read through 0005's chain machine, must each be verified, and are checked before anyone signs; without that evidence nothing is signed. The check covers the setup those reads can see, which leaves out an owner or module a delegatecall wrote outside Freedom ([what the setup check can't see](#what-the-setup-check-cant-see)). The executor's transaction is prepared by the core. protocol-kit leaves the browser.
- **Approvals:** a Ledger's signatures, a Safe's Ledger owner's included, become enforced in the core, as 0012's other signatures are. A Safe's vault owners' and executor's already are, from 0012's APR-4, through Safe approvals. A `safe-send` token binds the whole SafeTx the core built, not only its `to`, `value` and `data`.
- **Vectors:** recorded APDU exchanges from the JS reference over a scripted device, and from real devices for a smaller set; Safe vectors from protocol-kit through the browser's own modules.
- **Steps:** LDG-1 to LDG-3 and SAFE-1 to SAFE-3.
- **Found while checking the code:** Ledger signatures were used unchecked (F-1, fixed on `integration/rust-core` by #1063 but for a few answers); hw-app-eth sends some typed data wrong (F-2); an added Ledger account's address was the chrome's word (F-3, fixed by #1065); a Safe's address rests on one endpoint's answer (F-4, since fixed by #1066); two smaller ones (F-5, F-6), each a public browser issue, #1063 to #1068; and, from LDG-1's vectors, a chain ID of 2^53 or more can't be signed on a Ledger (F-7). See [Facts](#facts-found-while-checking-the-code).

## Goals and non-goals

**Goals**
- **Main never chooses a byte the device signs,** but the nonce, which it keeps choosing under the account's lock until 0013 moves the intent journal (0012, *Transaction building*).
- **No device signature is used before the core checks it.**
- **A faulty core can't make the device sign** anything main didn't derive itself from the request it sent or the approval it recorded.
- **No Safe transaction, address or calldata that the core didn't build.**
- **No Safe read on one endpoint's word** where the chain machine can do better.
- **Enforced approvals** for both, as 0012 enforces the vault's, and a Safe's vault owners' and executor's through its Safe approvals.
- **Parity** with the JS reference, shown by vectors, with every [deviation](#deviations) listed.
- **Bounded, cancellable device work.**

**Non-goals**
- **A compromised main.** Stage 1 trusts main (0001). It holds the device, so it can send its own APDUs. The device's screen is the last check.
- **Clear signing with Ledger's metadata services** (token and plugin descriptors, EIP-712 filters). They stay off, as today, since they send the request to hosted services (`signer.js:14–25`). A bundled offline registry is a later decision.
- **Other hardware wallets, Ledger over Bluetooth, and mobile's transport.** `fc-ledger` is sans-I/O, so mobile can drive it later through its own transport.
- **Other Safe versions or chains, Safes made elsewhere, modules and owner changes** ([Q24](#open-questions)).
- **Safe's hosted Transaction Service:** never, as today (`safe-executor.js:11–12`).
- **Phone accounts,** including phone owners of a Safe: 0012's phone jobs.

## Today

### Ledger

- **The transport** (`transport.js`): `@ledgerhq/hw-transport-node-hid` over node-hid. It opens the first Ledger it finds for each operation and closes it after (`TransportNodeHid.open('')`, 81–93), and one queue serializes all device access (66–98). hw-app-eth's `Eth` is built with every hosted lookup off (`OFFLINE_LOAD_CONFIG`, 58–64). `readAddresses` reads several paths in one session, display off (140–149), for adding an account and for the record check below.
- **Discovery** (`ledger:get-accounts`, `ipc.js:24–38`): `getAddress(path, false)` for 1 to 20 paths (`transport.js:112–129`) of two schemes: `live`, `44'/60'/i'/0/0`, and `legacy`, `44'/60'/0'/i` (35–44). The address is never shown on the device: "verification on-device happens when the user confirms their first signature" (104–107). The same handler then checks the Ledger records no device has matched yet against the attached one (`account-checks.js:27–50`, #1065): a second session reads each such record's path, the core keeps each answer on its record (`accounts.record_address_check`), and the records it doesn't hold come back as `mismatched`; a failed check doesn't fail discovery. The connect screen polls it every 1.5 s (`connect-ledger.js:18`), the Safe board every 2 s (`safe-signing.js:693–713`).
- **Adding** (`wallet:add-ledger-wallet`, `identity-manager.js:1952–1959`): the chrome sends a name, an address and a path. Main checks that the path is a non-empty string and that the address parses (1388–1394), reads the address at that path from the device, display off (`readAddresses`, 1395–1396), and refuses another, `LEDGER_ADDRESS_MISMATCH` (1397–1399, #1065). The core adds the record, `matched` (`accounts.add_ledger`, 1402). A record added before #1065 starts `unchecked`, and a Safe's device owner must be `matched` (`addSafeWallet`, 1523–1529).
- **Signing** (`signer.js`). Every operation first reads the address at the record's path and refuses another (`LEDGER_WRONG_DEVICE`, 120–149), keeping the answer on the record (`onAddressCheck`), and awaits the caller's last check (`beforeSign`) right before each signing APDU. Every signature is recovered against the record's address before it leaves (56–97, #1063; [F-1](#facts-found-while-checking-the-code)). Then:
  - **a transaction:** ethers' unsigned serialization goes to `signTransaction(path, raw, null)`, and the signed bytes are parsed back, their sender the account (154–178). With no resolution a contract call shows as raw data, and the app refuses it unless its blind-signing setting is on (`0x6a80`, `errors.js:74`);
  - **a message:** `signPersonalMessage`, recovered over its EIP-191 hash (180–189);
  - **typed data:** main first hashes it through the core and compares the hash with the confirmed one (`signers.js:439–449`). Then `signEIP712Message` sends every type and value. On status `0x6d00` (instruction not supported) to any of its APDUs, `B0 01` and `E0 0C 00 01` included, it falls back to `signEIP712HashedMessage` with ethers' domain separator and struct hash (`signer.js:197–216`). The signature is recovered over the core's hash (`digest`), never one rebuilt from what the device was sent (217–222). hw-app-eth's own note: the field method "is not compatible with nano S (LNS)" (`Eth.js:318`).
  - **an x402 payment** (#392, 0012's *x402*): the core's `x402.authorize { device }` returns the typed data `@x402/evm` hands its signer, and its hash; main has the Ledger sign that typed data through the signer factory, which checks the core's hash, and `x402.settle` checks the signature (`x402/sign-flow.js:104–137`). Main builds no authorization.
- **The APDUs** hw-app-eth sends for these, with no resolution and no filters:

  | APDU | CLA INS P1 P2 | Data | Sent by |
  |---|---|---|---|
  | get address | `E0 02 00 00` (`01` to display) | path | `Eth.js:102–132` |
  | app name and version | `B0 01 00 00` | — | `EIP712/utils.js:244–258`, typed data only |
  | sign a transaction | `E0 04 00 00`, then `E0 04 80 00` | path ‖ unsigned RLP, in pieces of at most 255 bytes | `Eth.js:147–223`, `utils.js:202–247` |

  | EIP-712 type definitions | `E0 1A 00 00` (a type's name), `E0 1A 00 FF` (a field) | names and type descriptors | `EIP712/index.js:114–129` |
  | EIP-712 values | `E0 1C 00 00` (a root), `E0 1C 00 0F` (an array's length), `E0 1C 01 FF` / `00 FF` (a value's pieces) | the values | `EIP712/index.js:149–190` |
  | EIP-712 sign, fields | `E0 0C 00 01` | path | `EIP712/index.js:396–410` |
  | EIP-712 sign, hash only | `E0 0C 00 00` | path ‖ domain separator ‖ struct hash | `EIP712/index.js:428–452` |

- **App checks:** Freedom checks neither the app's name nor its version. hw-app-eth reads `B0 01` inside `signEIP712Message` only to choose a filter format (`EIP712/index.js:323–325`), and no filter is ever sent, since the lookups are off.
- **Errors:** status words and transport errors map to twelve `LEDGER_*` codes with fixed texts (`errors.js:12–49`), #1063's `BAD_SIGNATURE` and #1065's `ADDRESS_MISMATCH` and `ACCOUNT_UNCHECKED` among them; the status table is 65–79, the error names 82–94. No Ledger attached, which hw-transport-node-hid reports as `TransportError("NoDevice")`, matches none of them: it is `LEDGER_UNKNOWN`, "Ledger error. Reconnect the device and try again." (`vectors/ledger.json`'s `open-no-device-*`); node-hid's "cannot open device" is `LEDGER_DEVICE_NOT_FOUND`.
- **Waiting:** nothing has a deadline. node-hid's `exchange` reads until the device answers (`TransportNodeHid.js:132–159`); hw-transport's 15 s `unresponsiveTimeout` only emits an event (`Transport.js:251–290`); and its `close()` waits for the exchange in flight (`TransportNodeHid.js:162–165`). A signature holds the device queue and the account's nonce lock, whose holder "is never cut short" (`nonce-reservations.js:18–19`). The send screen's Ledger state has no Cancel (`send.js:479–495`), and the dApp approval disables Reject and Back while it signs (`dapp-tx.js:519–523`). Only the device, or unplugging it, ends a signature.
- **Unplugged:** node-hid's read or write fails, which maps to `LEDGER_DISCONNECTED` (`errors.js:86–87`). Nothing is signed, and a send releases its nonce (`nonce-reservations.js:15–17`).

- **Creating:** main resolves the owners' indexes to their addresses, draws a 128-bit salt (`safe-service.js:52–54`), computes the CREATE2 address from the pinned deployment with no chain read (`predictSafeAddress` and `pinnedDeployment`, `safe-executor.js:167–202`, `281–283`) and stores the record frozen through the core (`safe-service.js:92–102`). The deployment is built the same way (`buildDeploymentTransaction`, 294–298); its factory is compared with safe-deployments' canonical one (`assertCanonicalFactory`, 222–231), which the pinned one always is.
- **Building a SafeTx:** the address from the pinned deployment, and refused when the record's stored address isn't it ("Safe address mismatch", `safe-executor.js:317–329`). Then protocol-kit's `createTransaction` with `{ to, value, data }` (338–340). It sets operation CALL, the three gas fields 0, no gas token or refund receiver, and the nonce from the chain, read as a JS number (`standardizeSafeTransactionData`, `index.cjs:5864–5934`), so a nonce past 2^53 − 1 can't be hashed (ethers refuses it). Then `generateTypedData` and ethers' hash (`hashSafeTransaction`, `safe-executor.js:243–258`).
- **Chain reads:** protocol-kit and main's nonce read go through `getEip1193Provider` (`provider-manager.js:124–142`): the first endpoint that answers, with no quorum and no proof, outside 0005's router (0005, "Paths that bypass the router"). For a SafeTx protocol-kit reads `eth_chainId`, `eth_accounts` and `eth_getCode`, and for a deployed Safe `VERSION()` and `nonce()`; it no longer reads `proxyCreationCode()` for the address (`stub-chain.js` answers each). Main reads `nonce()` before it executes (`safe-transactions.js:193–200`). Whether the Safe is deployed is read through the core's router, and only a `verified` answer marks it (`isDeployedOnChain`, `safe-service.js:130–150`, #1066).
- **Approval:** the `safe-send` token binds the Safe's index, the chain, `to`, `value`, `data` and the site (`signing-confirmation.js:357–369`). `wallet:safe-send` reserves the Safe's one pending SafeTx, spends the token for its Safe approval, and then builds the SafeTx (`wallet-ipc.js:589–628`); a site's goes through `page-core-sends.js`'s `safeSend` (709–).
- **Owner signatures:** vault owners sign silently when the SafeTx is made and whenever the board opens (`collectFreeSignatures`, `signature-collection.js:131–194`); a device owner signs when the user taps its row (`signEntryOwner`, 212–279), refused for a record that isn't an owner, and not asked again of one that signed. Each signature is recovered against its owner with ethers' `verifyTypedData` (`safe-executor.js:369–386`), and kept as it came. Execution needs as many as the record's threshold (`safe-transactions.js:501–505`). The Safe's own owners and threshold are never read.
- **Execution:** the executor is the first vault owner (`pickDefaultExecutor`, `safe-executor.js:678–685`). protocol-kit's `EthSafeTransaction` keeps one signature per signer and joins them sorted (`buildSignatureBytes`), and ethers encodes `execTransaction` (`safe-executor.js:582–599`). A Safe nonce already past the SafeTx's makes it `superseded` (`safe-transactions.js:493–499`); one below it is not checked.
- **Messages (EIP-1271):** a SafeMessage `{ message: digest }` under the domain `{ chainId: 100, verifyingContract: safe }` (`safe-messages.js:367–377`). The digest is EIP-191's for `personal_sign` and the core's EIP-712 hash for typed data (`requestDigest`, 126–137). Sessions live in memory, bound to the requesting page and a random token (`randomUUID`, 422–436; `requireSession`, 236–249). The threshold's last signature ends the session's Safe approval, so no owner signs after it (76–80). `buildSignatureBytes` joins the signatures (`completeSafeMessage`, 501–524).
- **The pending store:** `safe-pending.json` is the core's since PRF-6(d) (`pending-store.js:1–49`): the core writes it with fc-wallet-state's codec, atomically, and renames an unreadable file aside (0013's `safe-pending-unreadable`); main keeps a copy and writes through the core.

### Facts found while checking the code

1. **F-1: Ledger signatures were used unchecked** (freedom-browser #1063). At `32532528` the Ledger backend returned whatever `r`, `s` and `v` the device sent, for a transaction, a message and typed data, so a device or library fault that signs another digest (F-2) reached the site as the confirmed signature. Fixed on `integration/rust-core` (`d3c467111`, `5fb758348`): `signer.js` recovers every signature against the record's address before it leaves (56–97, 154–224), a transaction's sender from the signed bytes, a message over its EIP-191 hash, typed data over the hash the core confirmed, and anything else is `LEDGER_BAD_SIGNATURE`. What it still takes, from `vectors/ledger.json` (recorded in a comment on freedom-browser#1063): a type 0 signature whose `s` is in the high half, which ethers parses and recovers, so the raw transaction main journals carries an `s` nodes refuse (`answer-tx-type0-high-s`); the first 65 bytes of a longer answer (`answer-*-long`); and a type 0 `v` of 27 or 28 ends `LEDGER_UNKNOWN` (hw-app-eth's `getParity`, "Invalid v value"), not `LEDGER_BAD_SIGNATURE`. The core's checks refuse all three ([Answers the core checks](#answers-the-core-checks), `signature-check`).
2. **F-2: hw-app-eth sends some typed data wrong** (freedom-browser #1064). Four faults in hw-app-eth 7.11.1's `lib/modules/EIP712/`, shown by running its own `signEIP712Message` (7.10.0's identical code, from the reference checkout) against a recording transport:
   - **A value loses its last bytes** when its encoding (a 2-byte length, then the value) is 255·n + 1 to 256·n bytes long: the pieces are counted per 256 bytes but cut per 255 (`index.js:180–182`). A 254-byte string goes as 255 of its 256 bytes, and a 510-byte one as 510 of 512.
   - **An array of more than 255 entries is announced with a wrong count:** the count's hex is cut to one byte (`intAsHexBytes(value, 1)`, `index.js:165`, `utils.js:89`), and `Buffer.from(…, 'hex')` drops the odd digit. 256 entries are announced as 16, and 300 as 18. A fixed array's size and the length of a type or field name over 255 are cut the same way (`EIP712/utils.js:176`, `186`, `193`).
   - **A definition over 255 bytes** is refused by hw-transport (`DataLengthTooBig`, `Transport.js:188–191`), so the user sees "Ledger error". A field's descriptor is its type byte, its size or its custom type's name with a length byte, and its name with a length byte, so a string field's name of 254 ASCII characters already makes 256 bytes, a sized field's of 253, a referenced type's name of 252, and a primary type's name of 256 (`vectors/ledger.json`'s `name-*` cases). That holds for any name; for a non-ASCII one the next fault also decides its length byte.
   - **A non-ASCII name is announced with its length in UTF-16 units, not bytes:** `makeTypeEntryStructBuffer` writes `name.length` before the name's UTF-8 bytes (`EIP712/utils.js:166–194`). A field named `é` is announced as 1 byte and takes 2, one named `😀` as 2 and takes 4, and a field of a custom type named `Té` names its type as 2 bytes and sends 3. ethers 6.17.0 accepts such names; 0002 refuses them ([Encodings](#the-apdu-grammar)).

   The fourth reaches the wire only for a name that fits an APDU: a short one, or one of up to 253 UTF-8 bytes for a string field. What a device does with the first, second and fourth isn't known without one. If it signs, it signs a digest of values the browser didn't show: at `32532528` F-1 returned that signature unchecked; since #1063 it doesn't recover over the confirmed hash, and main refuses it (`LEDGER_BAD_SIGNATURE`). Whether upstream knows of these hasn't been checked.
3. **F-3: an added Ledger account's address was the chrome's word** (freedom-browser #1065). At `32532528` `wallet:add-ledger-wallet` stored the address and path the chrome sent and never asked the device, so a compromised chrome could add a "Ledger" whose address the device doesn't hold, and make it an owner of a new Safe, where as one of a 1-of-2 Safe's owners it controls the Safe alone. Fixed on `integration/rust-core` (`75beb9410`): main reads the address at the path from the device, display off, and refuses another (`LEDGER_ADDRESS_MISMATCH`, `identity-manager.js:1387–1404`); a record added before that starts `unchecked`, discovery checks it against the attached device (`account-checks.js`), and a Safe's device owner must be `matched` (1523–1529). The device still never shows the address: question 3's display is the core's (`address-from-device`).
4. **F-4: a Safe's address rests on one endpoint's answer** (freedom-browser #1066).
   - **Fixed in the reference since** (`dea09d2f5`, #1066; amended for SAFE-1): the reference pins the deployment and the proxy code and computes the address and the deployment itself, with no chain read (`safe-executor.js:72–202`); it refuses a SafeTx and an activation for a record whose address isn't the derived one (325–329; `SAFE_ADDRESS_MISMATCH`, `safe-service.js:152–165`); and only a verified `eth_getCode` read or a verified receipt marks a record deployed (`safe-service.js:104–150`, `310–340`, `deployed-mark.js`). Its own test shows a lying `proxyCreationCode()` answer can't move the address (`safe-executor.test.js:198`), and so does `safe.json`'s `lying-proxy-code` case. What this design adds is the rest of the reads: the nonce, the owners and the setup, verified ([Chain reads](#chain-reads)). As found at `32532528`:
   - protocol-kit computes the CREATE2 address from `proxyCreationCode()`, which it reads from the factory (`index.cjs:6740–6756`, `6859`) through `getEip1193Provider`, at creation (`safe-service.js:86–96`). A wrong answer gives an address no deployment can reach, and funds sent there before activation are lost.
   - Activation deploys at the address the current answer gives, and marks the record deployed without comparing that address with the record's (`safe-service.js:225–247`).
   - `isDeployedOnChain` marks a record deployed for good on one endpoint's `eth_getCode` (103–113). Activation is then never offered again.
   - The code is a constant of the canonical factory: `stub-chain.js` records it, 486 bytes, keccak256 `0x1856e0ee08399d74e0ea0b03adca210aeade6f748969ac023cdcb4dd62dcaf5f`.
5. **F-5: an empty `personal_sign` fails on a Ledger** (freedom-browser #1067), with "Ledger error. Reconnect the device and try again." hw-app-eth's loop sends no APDU for a message of 0 bytes and then reads `response[0]` of nothing (`Eth.js:277–295`), which maps to `LEDGER_UNKNOWN`. Low.
6. **F-6: a torn `safe-pending.json` loses every half-signed Safe transaction** (freedom-browser #1068). It is written in place, and a file that doesn't parse loads as `{}`, which the next write saves (`pending-store.js:28–41`). The device signatures collected for those transactions go with it. 0013 lists the file as written in place; this is the consequence.
   - **Fixed since** (`dea09d2f5`; amended for SAFE-1): the file is the core's (0013's PRF-6(d)), written atomically with fc-wallet-state's codec, and an unreadable one is renamed aside and reported (0013's `safe-pending-unreadable`), so deviation `pending-atomic` is today's behavior.
7. **F-7: a chain ID of 2^53 or more can't be signed on a Ledger** (found by LDG-1's vectors; filed upstream as LedgerHQ/ledger-live#25605: hw-app-eth, still present on its default branch at 7.14.0). hw-app-eth parses the unsigned transaction with ethers v5 (`ledgerService.parseTransaction`, `Eth.js:200`), whose `toNumber` overflows: a type 2's parse throws before its first piece (`LEDGER_UNKNOWN`), and a type 0's chain ID reads as 0, so `getV` returns the device's byte as `v` and the recovery refuses the signature (`LEDGER_BAD_SIGNATURE`). 0002 signs every such chain ID for a vault account. The core reads `v` from the bound chain ID ([Answers the core checks](#answers-the-core-checks), `chain-id-width`).

## Threat model

Stage 1 trusts main (0001). The attackers are 0011's and 0012's: a compromised chrome renderer, a bug in main, and whoever reaches a signature through one; and for these two features, a site's request, one lying RPC endpoint, a fault in a library or a device, and a faulty core. The core holds the vault's keys, so main can't contain it there; a Ledger's key is the one it doesn't hold, and main's grammar is what keeps a faulty core from using it.

| The attacker wants to | Today | After LDG-3 and SAFE-3 |
|---|---|---|
| Have the device sign bytes the approval didn't cover (a main bug) | Yes: main builds every APDU | No. The core builds them and main derives them again; a main bug that changes one gets a signature the core refuses. The nonce stays main's (0012) |
| Swap the typed data, SafeTx or SafeMessage of a live Ledger signature for another of the same shape (a faulty core) | — (the core sends no APDU today) | No: main derives every APDU byte from the request it sent or the approval it recorded, and refuses any other before the device ([Main's typed-data binding](#mains-typed-data-binding)) |
| Have a Ledger sign another x402 schema, spender or time window (a faulty core) | Yes: the core builds the authorization (#392), and main has the device sign its typed data, checked against the core's own hash only | No: main rebuilds the whole authorization from the accept entry, its own clock and the core's nonce, and sends its own copy ([x402 from a Ledger account](#x402-from-a-ledger-account)) |
| Have a Ledger sign a SafeTx the user discarded, through a stale approval (a faulty core) | — | No: approval records live in main's memory only, and are dropped before a discard reaches the core ([Approval records](#approval-records)) |
| Pass a signature over something else as the confirmed one (F-2, a stale answer, a device fault) | No since #1063, but a type 0's high `s` and a longer answer's first 65 bytes pass (F-1) | No: recovered against the account and the confirmed digest |
| Get a typed-data signature the device shows only as two hashes (a site that targets a Nano S) | Yes: the fallback | Yes, kept ([Q23](#open-questions)): only after the device's `6D00`, over `fc-evm`'s hashes of the bound typed data, with a warning on screen before the device asks, a notice where no approval shows |
| List an address the device doesn't hold (chrome) | No since #1065: main reads the device's, display off, and checks an older record at discovery (F-3) | No: the core reads it from the device |
| Hold the device and the account's sends indefinitely (a request left on the device) | Yes | No: 5 minutes, and a Cancel |
| Make a new Safe's address unreachable (one endpoint) | No since #1066: the reference pins the constants (F-4, yes at `32532528`) | No: the address uses pinned constants and no chain read |
| Mark an undeployed Safe deployed, or deploy elsewhere (one endpoint) | No since #1066: only a verified read or receipt marks it, and activation compares the address (F-4, yes at `32532528`) | No on a verified read; otherwise the router's answer, and activation compares the address |
| Have owners sign a SafeTx whose operation, gas, refund or nonce fields the prompt didn't cover (a main bug) | Yes: the token binds only `to`, `value` and `data`, and the Safe pays a refund out of its own balance | No: the token binds the whole SafeTx the core built |
| Execute for a Safe whose owners or threshold were changed elsewhere | The record's owners and threshold count | Refused when the change shows in the setup reads ([Q24](#open-questions)); an unlinked owner or module isn't seen (next rows) |
| Report the record's setup for a Safe that was changed (one lying endpoint) | The setup isn't read | No: every read the decision rests on must be verified, or nothing is signed ([Chain reads](#chain-reads)) |
| Change the Safe's own setup through a site's transaction | Yes, like any call | No: refused, `safe_self_call` ([question 4](#open-questions)) |
| Add a hidden owner or module through a delegatecall signed outside Freedom | Yes, and nothing reads it | Not detected: it takes the threshold of the user's own keys signing outside Freedom, and Freedom never builds a delegatecall ([what the setup check can't see](#what-the-setup-check-cant-see)) |
| Sign with the executor's key for something other than a ready SafeTx (a main bug) | Yes, under `shell` | No: only the core's prepared send, or an `executor-send` token for a fee the check stopped |
| Act as main | Everything | Everything: main holds the device and relays its answers |

**What stays open:**
- **A compromised main** can drive the device itself, and it sees every answer the device sends.
- **What the device shows** for a contract call is raw data with clear signing off, and needs the app's blind-signing setting. The core can't change that.
- **A user who approves on the device without reading.**
- **Typed data on a Ledger that can't show its fields** (a Nano S): the device shows only two hashes, and the browser's view is the only display ([Q23](#open-questions)).
- **The chrome's wallet kinds** until APS-3 (0011, 0012).
- **Unverified reads for display only** (a balance, an activation cost): the router's quorum or one endpoint decides them, as the user's policy sets. No signature or execution rests on one.

## Ledger

### Where the device lives

**Proposed: main keeps the USB HID device, and the core sends it APDUs through main.**
- **Main** keeps `@ledgerhq/hw-transport-node-hid` for the device's HID framing, and drops `@ledgerhq/hw-app-eth` with what it pulls in (`axios`, `@ledgerhq/domain-service`, `@ledgerhq/evm-tools`). It uses three things: `TransportNodeHid.open`, `exchange`, and, to cancel, a close of the node-hid handle. The transport's own `close()` can't cancel, since it waits for the exchange in flight.
- **The core** builds each APDU from the request it authorized and the account's record, reads each answer, and assembles and checks the signature. It holds no key for it.
- **Why not HID in the core:** it would add a C library (hidapi) and per-OS device code to the core, and a device grant to D7's confinement later (0010). Mobile needs Bluetooth and its own transport anyway. And in Stage 1 main is trusted, so taking the device from main protects against nothing that the checks below don't already cover ([Options weighed](#options-weighed)).

### The device lane

- **One operation at a time,** browser-wide, as today's queue. At most 8 wait, in order; a ninth is refused `LEDGER_BUSY`. A wait counts against the operation's 5 minutes (open: [question 5](#open-questions)).
- **Main's hang watchdog** (decided 2026-11-26) is chosen by main from the method's class and the request's params. `schema.json`'s `device` class stays on every row it marks.
  - **A device request,** one main can see will use the device, gets the lane's watchdog. Its params decide it, as [the API](#api) has them:
    - `sign.transaction`, `sign.message`, `sign.typed_data`: `key.kind` is `"ledger"`, the Ledger key reference;
    - `ledger.accounts` and `ledger.add`: every request;
    - `x402.settle`: its Ledger form, `{ reservation, typed_data }`;
    - `safe.sign_owner` (a pending SafeTx) and `safe.message_sign` (a SafeMessage session): an `owner` whose record is a Ledger's.
  - **Every other request of these methods** keeps 0001's immediate watchdog of 15 s, as today: a `sign.*` with a vault key or any other key, and `x402.settle { reservation, outcome }` and `{ reservation, signature }`. `safe.sign_owner` and `safe.message_sign` are the exception, below.
  - **`safe.sign_owner` and `safe.message_sign` read the chain first,** the verified setup reads before each owner's signature ([Chain reads](#chain-reads)), so each one's watchdog starts from the chain machine's request bound, 120 s, as `chain.request`'s. For vault owners (no `owner`, or a vault owner's), which send no `shell.ledger_apdu`, it is that bound plus 0001's 15 s margin: 135 s. For a Ledger owner, until its first `shell.ledger_apdu`, it is the bound plus the lane's longest wait in the queue plus the margin: 7 minutes and 15 s; from each `shell.ledger_apdu` on, the per-APDU rule below. A phone owner's is PHN-1's to set.
  - **The lane's watchdog,** under either answer to question 5. Until a `shell.ledger_apdu` first names the request in `for`, it is the lane's longest wait in the queue plus 0001's 15 s margin: 5 minutes and 15 s (a Ledger owner's `safe.sign_owner` or `safe.message_sign` adds its reads' 120 s, above). Under today's text the wait counts against the operation's 5 minutes, and under question 5's proposal it is capped on its own at 5, so a request queued behind another is never killed at 15 s. From each `shell.ledger_apdu` on, it is that APDU's `deadline_ms` plus the 15 s margin: 30 s, or 5 minutes and 15 s for the APDU that waits for the user. Each APDU, and each answer to one, resets it. When the request ends, the watchdog ends.
  - **The core may not keep a device request queued past the lane's limit,** and LDG-2's L2 enforces that. Main's side, freedom-browser's `core-deadlines.js` and `service-client.js`, implements these watchdogs in LDG-3.
  - **The other `safe.*` methods that read the chain** take the same chain watchdog, 120 s plus the margin, 135 s ([API](#api)).
- **Discovery doesn't wait:** while an operation runs, `ledger.accounts` answers `LEDGER_BUSY` at once (deviation `discovery-busy`). Today a poll waits behind a signature.
- **An operation belongs to one core request,** its parent: a `sign.*` request with a Ledger key, `ledger.accounts`, `ledger.add`, `x402.settle { reservation, typed_data }` for a Ledger account ([x402 from a Ledger account](#x402-from-a-ledger-account)), `safe.sign_owner` for a Ledger owner of a pending SafeTx, or `safe.message_sign` for a Ledger owner of a SafeMessage session ([Messages](#messages-eip-1271)). Main opens the device at the operation's first APDU and closes it when the parent ends, so Ledger Live can use the device in between, as today.
- **The vault:** no vault key is used, so the core doesn't require it unlocked for a Ledger key. Main's gates before the prompt stay as they are.

### `shell.ledger_apdu`

A core-to-main request, like 0004's `shell.*`:

| Params | Main does | Reply |
|---|---|---|
| `{ for, apdu, deadline_ms }`: the parent's envelope ID; one APDU, hex, 5 to 260 bytes (`CLA INS P1 P2 Lc data`, `Lc` ≤ 255); and the exchange's deadline, `15000`, or `300000` for the APDU that waits for the user to confirm (the row's *Waits for the user*) | checks the APDU against the [grammar](#the-apdu-grammar) for `for` at its step; opens the device on the operation's first APDU; one `exchange`, under `deadline_ms` | `{ answer }`: hex, 2 to 260 bytes, ending in the status word. For a `6D00` to the operation's first `E0 1A`, `{ answer, hash_only: "shown" }`, sent only once the hash-only warning is on screen ([Typed data on the device](#typed-data-on-the-device-q23)). Or `{ failed }`: `not_found`, `busy`, `disconnected`, `unresponsive` or `timeout` |

- **Read strictly both ways,** as 0015 reads `shell.swarm_api`: an unknown member, a wrong type or an answer outside its bounds is `invalid_argument` from main, and a protocol error in the core. So is `hash_only` on any other answer. Main's error is one of two (as built): `invalid_argument` with `data: { rule }` for an APDU it refused ([below](#the-apdu-grammar)), and `cancelled`, without data, for the core's cancel; any other is a protocol error too.
- **Main closes the device** when the parent ends, on a cancel, on a `failed`, and on a refused APDU.
- **`deadline_ms` is a contract change** (2026-11-26): main reads the params strictly, so its relay must accept the member before the core sends it. LDG-2's lane (L2) sends it on every `shell.ledger_apdu`, and LDG-3's relay, written from this design, reads it as one of its two values. The deadlines themselves are [below](#deadlines-cancel-and-unplugging).

### The APDU grammar

**Encodings.** `P` is a path: one byte, the number of elements `n`, then each element as 4 bytes, big-endian, with `0x80000000` set for a hardened one. Only the two schemes' forms are admitted: `44'/60'/i'/0/0` (`n` = 5) and `44'/60'/0'/i` (`n` = 4), with `i` from 0 to 2^31 − 1 (deviation `path-strict`: hw-app-eth's `splitPath` skips an element it can't read, `utils.js:52–67`). `T` is the unsigned serialization of the bound transaction, the payload 0002's `sign.transaction` signs: for type 0, `rlp([nonce, gasPrice, gasLimit, to, value, data, chainId, 0, 0])`; for type 2, `0x02 ‖ rlp([chainId, nonce, maxPriorityFeePerGas, maxFeePerGas, gasLimit, to, value, data, []])`. **Names are ASCII:** 0002 refuses a type or field name outside `[A-Za-z_$][A-Za-z0-9_$]*` before anything is hashed, so a name's length in bytes is its length in characters, and its one-byte prefix is that count, at most 255 ([Bounds](#bounds)). hw-app-eth announces a non-ASCII name's length in UTF-16 units (F-2); the core never sends one (deviation `name-ascii`).

**The rows** are normative. Each operation is its APDUs in this order, and no other.

| Operation | APDUs, in order | Bytes, all from | Waits for the user |
|---|---|---|---|
| `ledger.accounts`, `c` from 1 to 20, then `r` from 0 to 20 | `E0 02 00 00` `P(path_k)`, `c` times; then `E0 02 00 00` `P(path_j)`, `r` times | the scheme's paths for `start` … `start + c − 1`; then the path of each Ledger record no device has matched, at most 20 ([Accounts](#accounts)) | no |
| `ledger.add` | `E0 02 01 00` `P` (question 3) | the path asked | yes, with the display |
| every signature, first | `E0 02 00 00` `P`, once | the record's path | no |
| every signature, second | `B0 01 00 00`, no data, once | — | no |
| `sign.transaction` | `E0 04 00 00` with the first piece, then `E0 04 80 00` with each other piece of `P ‖ T` | the bound transaction (nonce included, which main chose). Pieces of 255 bytes; for type 0, the size hw-app-eth's `safeChunkTransaction` picks so that no piece ends where a legacy transaction could (`utils.js:202–247`) | the last piece |
| `sign.message` | `E0 08 00 00` with `P ‖ len(m)` (4 bytes, big-endian) and the first `150 − 5 − 4n` bytes of `m`, then `E0 08 80 00` with each next 150 bytes | the bound bytes `m`, at least 1 (deviation `empty-message`, F-5) | the last |
| `sign.typed_data`: definitions | for each type, its names in ascending order (as `sortObjectAlphabetically` sorts them, evm-tools `message/EIP712/index.js:23–35`): `E0 1A 00 00` its name, then `E0 1A 00 FF` for each field in order | the bound typed data's types, `EIP712Domain` built from the domain's keys, as ethers' `getPayload` builds it | no |
| `sign.typed_data`: values | `E0 1C 00 00` `"EIP712Domain"`; each domain value; `E0 1C 00 00` the primary type's name; each message value, depth first. An array: `E0 1C 00 0F` with its length, then its entries. A value: its encoding (2-byte length ‖ value bytes) in pieces of 255, `E0 1C 01 FF` for each but the last, `E0 1C 00 FF` for the last | the core's parse of the bound values, encoded as hw-app-eth's `EIP712_TYPE_ENCODERS` encode them (`EIP712/utils.js:62–102`), and cut as F-2 says they should be (deviation `field-pieces`) | no |
| `sign.typed_data`: sign | `E0 0C 00 01` `P`, once | the record's path | yes |
| the hash-only form (Q23) | `E0 0C 00 00` `P ‖ domainSeparator ‖ hashStruct(message)`, once, only after `6D00` answered the operation's first `E0 1A` and main's answer said `hash_only: "shown"` | `fc-evm`'s hashes of the bound typed data, not ethers' in main | yes |
| `x402.settle { typed_data }`, a Ledger account | as `sign.typed_data`, over the reserved authorization | main's own rebuild of it, which it sent as `typed_data` ([x402 from a Ledger account](#x402-from-a-ledger-account)) | yes |
| `safe.sign_owner`, a Ledger owner | as `sign.typed_data`, over the core's SafeTx | the approved SafeTx ([Owner signatures](#owner-signatures)), which main derives from its own record ([below](#mains-typed-data-binding)) | yes |
| `safe.message_sign`, a Ledger owner | as `sign.typed_data`, over the core's SafeMessage | the session's SafeMessage, which main derives from the page's request it holds ([below](#mains-typed-data-binding)) | yes |

**No free field.** Every byte of every APDU is derived twice: by the core, from the request it authorized and the record's path; and by main, from the request it sent or the approval it recorded, and the same path ([Main's typed-data binding](#mains-typed-data-binding)). Main compares the two byte for byte. No byte comes from an earlier answer of the device. The one value main takes from the core is a Ledger x402 payment's nonce, which names no recipient, amount, spender or time; the payment's times are main's own clock reading, which main sends to the core ([below](#mains-typed-data-binding)).

**What main checks,** for each `shell.ledger_apdu`, from what main itself knows: the parent it sent and its params, and the account's record.
- **The parent** is live and is one of the rows' operations, for a Ledger account.
- **Order and counts:** the APDU is the next its row allows. One at a time per operation.
- **Header and length:** `CLA INS P1 P2` as the row has them; `Lc` ≤ 255, and equal to the data's length.
- **The path** is the record's, wherever the row has `P`.
- **The payload,** for every row: main builds the operation's whole expected stream itself, and each APDU must equal the next one of it, header and data, byte for byte. For a transaction or a message that is `P ‖ T` or `P ‖ len(m) ‖ m` in the row's pieces, built from the parent's params with ethers, as `signing-utils.js` does today. For typed data it is the definitions and values main encodes itself ([below](#mains-typed-data-binding)).
- **The rare ones:** `E0 02 01 00` only under `ledger.add`; `E0 0C 00 00` only after a `6D00` answer to the operation's first `E0 1A`, which main sent as `{ answer, hash_only: "shown" }` once the hash-only warning was on screen (Q23).
- **A refused APDU** is answered `invalid_argument` with `data: { rule }` (`parent`, `order`, `header`, `count`, `path`, `payload` or `ended`), before any byte reaches the device. Main logs the rule, never an APDU's bytes, refuses every later APDU of that parent and closes the device. The core ends the parent with `LEDGER_UNKNOWN`.
- **One source:** the grammar is data, `vectors/ledger-grammar.json`: the rows, each row's honest APDUs, which must be admitted, and its nearest forbidden ones, which must be refused. The core's tests and main's relay suite both read it, as 0015's `swarm-grammar.json` is read. Three rows above are newer than the file (2026-11-26): `ledger.accounts`'s check of the unmatched records, which the file and the generator's discovery cases gain in LDG-2's L3; `x402.settle`'s, which they gain in L5; and `safe.message_sign`'s, split from the file's `safe.sign_owner` row, which covered the SafeTx and the SafeMessage both, so that a SafeMessage's `E0 0C` parent is `safe.message_sign` and a SafeTx's `safe.sign_owner`. That split lands with L3's regeneration of the file, or with S6 at the latest.

### Main's typed-data binding

Main encodes the whole typed-data stream itself, from what it holds, and compares every APDU with it byte for byte. The encoder is a new module in main (`wallet/ledger/apdu-binding.js`), written from this design, not taken from hw-app-eth.
- **`sign.typed_data`:** from the request main sent. Main first checks with ethers' `TypedDataEncoder.hash` that `typed_data` hashes to `expected_hash`, and refuses before the first APDU if it doesn't. Then it takes ethers' `getPayload`: the types with `EIP712Domain`, the primary type, the domain and the message, with integers as decimal strings. It encodes the definitions with the types in ascending order of their names and each field's descriptor, then the values depth first, each in pieces of 255, as [the rows](#the-apdu-grammar) say. After that `6D00` (Q23), it computes the hash-only APDU's two hashes with ethers too, shows them in the hash-only warning, and answers only once the warning is on screen ([Typed data on the device](#typed-data-on-the-device-q23)).
- **A SafeTx, for a Ledger owner:**
  - **At the approval,** main computes the SafeTx's hash itself, with ethers, from the fields the prompt showed (`safe.prepare`'s result), under the fixed `SafeTx` type and the domain of the Safe's address the prompt named, on chain 100. It requires that hash to equal the core's `safe_tx_hash`, and keeps it as its **approval record**: the Safe's index and address, the chain and the hash, one per Safe, before it sends `safe.propose`.
  - **At a Ledger owner's turn,** main reads the pending entry's fields (`safe.pending`), computes their hash again, and requires its own record's. It encodes the stream from those fields.
  - **The records live in main's memory only,** never in a file ([Approval records](#approval-records)). With no record (after any restart of main, a crash, or an older build run in between), the approvals surface shows the SafeTx, rebuilt by main from the fields, and the user approves it again before the device is asked. That decision records it again.
- **A SafeMessage, for a Ledger owner:** from the page's request main holds (0011's request record): the digest by ethers (`hashMessage` for `personal_sign`, `TypedDataEncoder.hash` for typed data), then `{ message: digest }` under the domain of the Safe's address on chain 100. Sessions live in memory, so nothing is written.
- **An x402 payment from a Ledger account** goes as `x402.settle { reservation, typed_data }`, its APDUs `sign.typed_data`'s, under [the x402 reconstruction](#x402-from-a-ledger-account) below: main rebuilds the whole authorization itself, sends its own copy, and encodes the stream from that copy.
- **Two derivations:** main encodes from ethers' parse, the core from `fc-evm`'s. Both must reproduce `ledger.json`'s APDUs, which is their joint contract. Where they would differ for an input the core accepts, main refuses: the operation fails closed with nothing signed, and the case is a vector to raise, not to edit.
- **The vault owners** of a Safe sign in the core, which holds their keys, so main's binding doesn't apply to them.
- **What this stops:** during a live `sign.typed_data`, or a Ledger `safe.sign_owner` or `safe.message_sign`, a faulty core can't send another schema, message, SafeTx or SafeMessage of the same shape. Any changed byte is a `payload` refusal, before the device.

### Approval records

A record is authority: it decides what a Ledger may sign without another approval. So it follows 0013's set-A rule for such state, a narrowing applied first and nothing restored that was taken away, though main holds it, as its own check on the core, rather than the core.
- **In memory only.** No file, so nothing outlives the process that made it. A stale record can't come back: not after a crash, not from a failed removal on disk, and not after an older build discards the SafeTx (an older build never sees the record, and the next start has none).
- **Narrowing first.** Main drops a Safe's record before it asks the core to discard the SafeTx, when `safe.execute` answers `superseded`, and when it reports `safe.executed`. A failure after that leaves no record. A pending entry the core still holds then needs a new approval before a Ledger signs it.
- **Recording last.** Main records a hash only on the user's decision on the approvals surface (the chrome's until APS-3, the approvals document after, as for every wallet kind), and only once its own hash equals the core's. If `safe.propose` then fails, main drops the record.
- **Bounds:** one record per Safe, as there is one pending SafeTx per Safe: a new approval replaces the Safe's old record. About 100 bytes each.
- **The cost:** after a restart, a Ledger owner's signature on a SafeTx approved before it needs one more approval. Vault owners sign in the core and aren't affected; neither are SafeMessages, whose sessions end with their page.

### x402 from a Ledger account

For a Ledger account, `x402.authorize` (0012's X402-1) checks the cap or the `x402-payment` token and charges the cap as for any account. It takes one more input, `now_s`: main's wall-clock reading in seconds, taken once for this payment. The core refuses a `now_s` more than 30 s from its own clock. Then it returns the authorization as typed data, with the nonce it drew, instead of signing it, and keeps it on the reservation. Main rebuilds the authorization itself, from the accept entry it holds, `now_s` and that nonce, and requires the core's typed data to equal its own in every type, field and value. It then sends its own copy back:
- **`x402.settle { reservation, typed_data }`** (new, decided 2026-11-26): the core requires `typed_data` to equal the reserved authorization, refuses anything else before the device, and signs it on the [device lane](#the-device-lane) with the account's record, as a Ledger key does (so `vault_meta` must be moved), and as `sign.typed_data`'s rows have it. The device's stream is bound to main's copy ([Main's typed-data binding](#mains-typed-data-binding)). The signature is checked as every Ledger signature is ([Answers the core checks](#answers-the-core-checks)), and the reply is a `{ signature }` settle's: `{ payload, charged, grant?, durable? }`. A refusal or failure on the device gives the cap's charge back and spends the reservation, as a refused `{ signature }` does.
- **`x402.settle { reservation, signature }`** (#392) stays: for a phone, and for a Ledger under main before LDG-3, which sends no `now_s`, so its authorization is #392's, built on the core's clock.

The binding is structural: the core signs only what it reserved, and only main's copy reaches the device. The two other ways, `sign.typed_data` with the Ledger key (this design as first written) and #392 as it is, are in [Options weighed](#options-weighed).

### Typed data on the device (Q23)

- **Field by field,** as today. The device receives every type and value, shows each field, and computes the digest itself. The core sends the values it parsed, so what the device shows is what the core's view shows (0002, #88), and the signature is checked against the hash the user confirmed.
- **No filters** (`E0 1E`), as today: they come from Ledger's hosted registry. The device shows raw field names and values.
- **The hash-only form** shows the user two hashes and nothing else. The browser's view is then the only display, and the device can't confirm it.
- **Decided (Q23, the user, 2026-11-24): the fallback stays,** with `fc-evm`'s hashes of the bound typed data, only after the device answers `6D00` to the operation's first `E0 1A`, and with a warning, on screen before the device asks, that the device shows only hashes (below). Its signature is recovered over the hash the token bound, as every typed-data signature is ([Answers the core checks](#answers-the-core-checks)). So a Nano S keeps signing typed data in Freedom: permits, x402 payments, sign-in requests that use typed data, and a Safe owner's SafeTx and SafeMessage. The refusal Q23 proposed, `LEDGER_TYPED_DATA_UNSUPPORTED` with nothing signed, isn't taken ([Options weighed](#options-weighed)).
- **The warning comes before the device asks.** Whether the device shows fields is learned only from the first `E0 1A`'s answer, after the request was approved. So on a `6D00` there, main holds its answer and first shows a hash-only warning state: "This Ledger can't show this request's fields. It will show two hashes instead: check them against the ones here before you confirm on the device," with the two hashes main computed ([Main's typed-data binding](#mains-typed-data-binding)).
  - **Where:** in the surface that waits on the device, where one is open: the approval's Ledger state (the chrome's until APS-3, the approvals document after), the wallet's own screen, or the Safe board's owner row. A request no surface shows, one a standing rule approved or an x402 payment, gets a notice in the chrome over the requesting tab instead, which stays until the operation ends.
  - **The signal:** only once the surface reports the state on screen does main answer, `{ answer, hash_only: "shown" }`, within the APDU's 15 s. The core sends `E0 0C 00 00` only after that answer, and main admits it only after sending it. A `6D00` answer without `hash_only` ends the operation with `LEDGER_UNKNOWN`, nothing signed.
- **Transactions with data** aren't part of Q23. The device itself decides how it shows a contract call, and with clear signing off it shows raw data and asks for its blind-signing setting.

### The app

- **Every signature** reads `B0 01` after the address check (deviation `app-check`: today only typed data reads it). The answer's format byte must be 1, and the name must be the Ethereum app's, `Ethereum` (LDG-3's device recordings pin it). Any other name ends the operation with `LEDGER_ETH_APP_NOT_OPEN`, as today's `6D00` and `6E00` do, and so does a format other than 1 (as built).
- **The version** is kept for the operation's error report only. Field mode is detected by the device's own answer (`6D00`), as today, not by a version table that differs by model.

### Answers the core checks

- **Status:** `9000` goes on. Any other status ends the operation with today's mapping (`errors.js:52–66`), never retried, except the one `6D00` of [Q23](#typed-data-on-the-device-q23), which the hash-only form follows.
- **Lengths:** an answer to an APDU that doesn't sign is exactly its status word, but for:
  - `E0 02`: `65 ‖ key (65 bytes) ‖ 40 ‖ address (40 ASCII hex)`. The address must be the one the key derives (keccak256 of its last 64 bytes; deviation `key-check`), and equal the record's;
  - `B0 01`: format, name and version, each within its length.

  An answer the core can't read ends the operation with `LEDGER_UNKNOWN` (as built): another length, a key that isn't an uncompressed one, an address that isn't 40 hex digits, or one that isn't the address its key derives (`key-check`). The address text is read by `fc-evm`'s `parse_address`: all lower case, all upper case, or mixed case with a valid EIP-55 checksum, so a mixed-case text with a bad checksum is unreadable too. The Ethereum app writes it EIP-55-checksummed (app-ethereum's `getEthAddressStringFromBinary`, under the app's own chain ID when the APDU names none, as the core's never does; only chain IDs 30 and 31 take EIP-1191's checksum instead).
- **A signature:** `v ‖ r ‖ s`, 65 bytes. For type 0, `v` is read as hw-app-eth's `getV` reads it: the device keeps one byte of `chainId'·2 + 35 + parity`, where `chainId'` is the chain ID's first four bytes (`utils.js:123–187`). Then:
  - **a transaction:** the core assembles the signed transaction, as hw-app-eth and ethers do, and recovers its sender, which must be the account;
  - **a message:** recovered over its EIP-191 hash;
  - **typed data:** recovered over the hash the token bound, never a hash rebuilt from what the device was sent;
  - `s` must be in the low half, as 0002's signatures are.

  Anything else is `LEDGER_BAD_SIGNATURE`: "The Ledger returned a signature that doesn't match this request. Nothing was sent." (deviation `signature-check`, F-1). Nothing a device sends leaves the core before these checks pass.

### Deadlines, cancel and unplugging

- **An APDU the user doesn't confirm:** 15 s, hw-transport's own `unresponsiveTimeout`, which today only warns. Then `LEDGER_UNRESPONSIVE`: "The Ledger stopped answering. Reconnect it and try again."
- **One the user confirms:** 5 minutes, as a phone job's (`remote/bridge.js:78`). Then `LEDGER_TIMEOUT`: "The Ledger wasn't confirmed in 5 minutes. If it still shows the request, reject it there." (deviation `device-deadlines`). Main enforces both on the exchange, as each `shell.ledger_apdu`'s `deadline_ms` names them (`15000` or `300000`); the core's own timer is 1 s longer.
- **Main's hang watchdog,** for a device request ([The device lane](#the-device-lane): a Ledger key's `sign.*`, `ledger.*`, `x402.settle`'s Ledger form, a Ledger owner's `safe.sign_owner` or `safe.message_sign`), gives each `shell.ledger_apdu` its `deadline_ms` plus 0001's 15 s margin, reset by each APDU and by its answer, and gives a request no `shell.ledger_apdu` has named yet 5 minutes and 15 s, the lane's longest wait in the queue plus the margin. So the core's timer, and the lane's limit on the queue, end the request before main's watchdog would. Every other request of a `device`-class method, a vault key's `sign.*` included, keeps 0001's immediate 15 s, but for `safe.sign_owner` and `safe.message_sign`, whose setup reads come first: 135 s for vault owners, and 7 minutes and 15 s before a Ledger owner's first `shell.ledger_apdu`. Main's `core-deadlines.js` and `service-client.js` implement it in LDG-3.
- **Cancel:** the parent's cancel (0001), when the user cancels, the prompt's handle closes (0011) or its document goes. The core cancels its pending `shell.ledger_apdu`; main closes the node-hid handle, which ends the read in flight; the parent replies `cancelled`. Its token was burnt when it was presented, as every token is (0012). The browser gains a Cancel in the send screen's Ledger state, and keeps Reject enabled in the dApp approval while the device waits (deviation `cancel`).
- **Unplugged:** a failed write or read is `{ failed: "disconnected" }`, `LEDGER_DISCONNECTED`. Nothing is signed, and a send releases its nonce, as today.
- **A late answer:** after a timeout or a cancel the handle is closed, so the answer has no reader. The next operation opens a new handle, starts with the address check, and recovers its signature against its own digest. An answer meant for another operation is never taken as this one's.
- **A device still showing an older request:** the new operation's first APDU gets an error status, or no answer in 15 s. It ends `LEDGER_BUSY` or `LEDGER_UNRESPONSIVE`, with nothing signed.
- **The core restarting** mid-operation: main closes the device when the core's connection ends, and the parent fails as any request does then (0001). **Main stopping:** the device keeps its prompt until the user rejects it, and its answer reaches no one.

### Bounds

- **Typed data a Ledger can't carry** is refused before the first APDU, with `LEDGER_TOO_LARGE` (deviation `device-bounds`): an array of more than 255 entries; a fixed array size or a number of dimensions above 255; a type or field name over 255 characters (which are bytes, since names are ASCII, [Encodings](#the-apdu-grammar)); a definition whose APDU would carry more than 255 bytes (a field's descriptor: its type byte, its size or its custom type's name with a length byte, its array dimensions, and its name with a length byte, so that a string field's name of 254 characters already makes 256 bytes, F-2); a value whose encoding is over 65,535 bytes (its own bytes, as built: its 2-byte length can say no more); or more than 2,048 APDUs in all (the address check and `B0 01` among them, as built).
- **Typed data a Ledger can't sign as written** is refused before the first APDU too, with `LEDGER_TYPE_NOT_CANONICAL`, "This request writes a type in a form a Ledger can't sign. Nothing was sent.": a field's array suffix written in any form but the one the device's `encodeType` rebuilds from the field's descriptor (`[]` or `[n]`, `n` in decimal with no leading zero), such as `uint8[02]`. The confirmed hash's `encodeType` keeps the written suffix, as ethers' does, and the device's has its own, so the digest the device signs couldn't be the confirmed one. This is the class of `vectors/ledger.json`'s `typed_data_excluded` case, `array-suffix-written-form`. Today the reference sends it and the device's signature fails the recovery, `LEDGER_BAD_SIGNATURE`; a vault account still signs it, as 0002 does.
- **APDUs per operation:** at most 2,048 (proposed), every APDU of the operation counted, the address check and `B0 01` included, so a message is at most about 300 KiB and a transaction's data about 500 KiB on a Ledger. LDG-3 measures the time per APDU on each model, and replaces the number if needed.
- **Memory:** the core builds each APDU as it goes from the parsed request, which 0002's limits already bound. One APDU and one answer are in flight, at most 260 bytes each. An operation's state is at most 64 KiB beyond its request. Main holds one APDU and one answer.
- **A reply's size** (as built): main's reply to one `shell.ledger_apdu` takes at most 584 bytes serialized, the largest answer's response at the largest ID (`{"type":"response","id":` and 16 digits, `,"result":{"answer":"`, 520 hex digits, `"}}`); every other form is shorter, main's fixed error messages included. A longer reply, whole or fragmented, is a protocol error before it is read (0015's D4).

### Accounts

- **`ledger.accounts { scheme, start, count }`** (chrome, shell) → `{ accounts: [{ path, address }], mismatched: [{ index, name, address, path }] }`, as `ledger:get-accounts` today: display off, 1 to 20 paths, each address checked against its key.
- **Discovery checks the unmatched records** (decided 2026-11-26), as `account-checks.js` does today: after its discovery APDUs, in the same operation, `ledger.accounts` reads `E0 02 00 00` `P` at the path of each Ledger record no device has matched (`unchecked` or `mismatched`), at most 20, in the wallet list's order, display off. The core records each result on its record itself, as `accounts.record_address_check` does, and the records the device doesn't hold come back in `mismatched`. A failed check, one the core can't record included, is logged and leaves `mismatched` empty; it doesn't fail discovery (`ipc.js:24–33`). So a record added before #1065 can own a Safe once a device that holds it is attached, without signing first (F-3; `identity-manager.js:1523–1529`). The reference checks every such record; the core at most 20 (deviation `check-bound`).
- **`ledger.add { scheme, index, name? }`** (chrome, shell): the core reads the address at that path from the device itself, with the display (question 3), and the user confirms there. Then it writes the record through 0013's `accounts.*` once PRF-6(a) has made `vault-meta.json` the core's. Until then it returns `{ path, address }`, and main writes exactly those. The chrome no longer sends an address (deviation `address-from-device`, F-3).
- **The key reference:** 0002's table gains `{ "kind": "ledger", "index": n }`, admitted in `sign.transaction`, `sign.message` and `sign.typed_data`. The core reads the record (decided 2026-11-26): a Ledger key requires `vault_meta` in the hello's `store_moved` (0013's PRF-6(a)), and answers `not_moved` otherwise. A caller may also send the record's `path` and `address`; each one given must equal the record's, or the key is refused.

## Safe

### Which Safes (Q24)

**Decided (Q24, the user, 2026-11-24): exactly the Safes Freedom creates today.** Anything else is refused with `safe_unsupported`, and supporting it is a design change.
- **Version 1.4.1,** with the three canonical contracts [above](#safe), as safe-deployments 1.37.66 lists them, and the factory's proxy code (F-4: 486 bytes, keccak256 `0x1856…af5f`). `fc-safe` pins all four, as the reference does since #1066. SAFE-1 checks them against safe-deployments' files, the reference's pins, the factory's recorded runtime code (whose keccak256 is the code hash safe-deployments lists, and which embeds the proxy code once) and the recorded `proxyCreationCode()` answer.
- **On Gnosis** (chain 100) only.
- **Two or three of the user's own accounts as owners,** 1 of 2 or 2 of 3, as the core's `accounts.addSafe` allows (fc-wallet-state's `add_safe`; `identity-manager.js:1523–1528`), set up with no setup call, no payment, no module, no guard and the canonical fallback handler.
- **As Freedom made it, still, as far as its setup can be read:** before each owner's signature and before execution, the core reads the Safe's setup ([Owners, threshold and setup](#owners-threshold-and-setup)), and refuses to go on when it isn't the record's. The reads see the Safe's linked owner and module lists, not every entry of its mappings ([what the check can't see](#what-the-setup-check-cant-see)).

### Built and hashed in the core

`fc-safe` (logic, no I/O) computes each of these from the record and the request, with no chain read:
- **The address:** CREATE2 from the factory, with salt keccak256(keccak256(`initializer`) ‖ the salt as a uint256) and init code hash keccak256(proxy code ‖ the singleton as a uint256), as the reference's `pinnedDeployment` does (`safe-executor.js:167–202`, #1066), with protocol-kit's `predictSafeAddress` formula (`index.cjs:6837–6895`). `initializer` is `setup(owners, threshold, 0x0, 0x, handler, 0x0, 0, 0x0)` (`encodeSetupCallData`, 6680–6730), owners in the record's order. A salt is decimal digits for a uint256 (leading zeros allowed, as `BigInt` reads them).
- **The deployment:** `createProxyWithNonce(singleton, initializer, salt)` to the factory.
- **The SafeTx:** `{ to, value, data, operation: 0, safeTxGas: 0, baseGas: 0, gasPrice: 0, gasToken: 0x0, refundReceiver: 0x0, nonce }`, today's values, with the nonce from the [chain](#chain-reads), at most 2^53 − 1: the reference can hash no larger one (protocol-kit reads the nonce as a JS number, and ethers refuses one past it), and `safe-pending.json` keeps it as a JSON number, so past it nothing is built. Its typed data under the domain `{ chainId: 100, verifyingContract: safe }`, with its fields in the reference's property order (which `safe-pending.json` keeps), and its hash through `fc-evm`. Read back from a pending entry's fields, it is refused the same way. A request for any other operation, gas field, gas token or refund receiver is refused; Freedom never makes one.
- **The SafeMessage:** `{ message: digest }` under the same domain. The digest is today's: EIP-191's for `personal_sign`, the core's EIP-712 hash for typed data.
- **The calldata** of `execTransaction`: the signatures sorted by owner address, each 65 bytes `r ‖ s ‖ v`, one per owner, as `buildSignatureBytes` joins them (`index.cjs:1343–1360`) from protocol-kit's `EthSafeTransaction`, which keeps one per signer. The ABI encoding uses `fc-naming`'s `abi::encode`.

### Chain reads

- **Through 0005's chain machine,** as the core's own reads, with the chain's sources and labels. Never protocol-kit's first endpoint (deviation `safe-reads`).
- **What is read:** `eth_getCode` at the Safe; `nonce()` (`0xaffed0e0`), `getOwners()` (`0xa0e67e2b`), `getThreshold()` (`0xe75235b8`) and `getModulesPaginated(0x1, 1)` (`0xcc2f8452`) by `eth_call`; and by `eth_getStorageAt`, slot 0 (the singleton), the guard's slot `0x4a20…34c8` and the fallback handler's `0x6c9a…18d5` (keccak256 of `guard_manager.guard.address` and `fallback_manager.handler.address`). `fc-safe` lists them with the code first and the nonce last, since the reads aren't pinned to one block, and sends each slot as all 32 bytes, as Colibri's prover requires (0014). As SAFE-2's S1 makes them (`freedom-cored`'s `safe::evidence`), at `latest`: the code alone first; then the six setup reads at once; then the nonce, once all six have answered. A step that decides ends the check there: no code, verified, is not deployed, and a read that isn't evidence, or another singleton, ends it before the nonce is read. Colibri proves the code and the slots but no call (main's #1046), so the four calls are verified only by a quorum of m ≥ 2, or by a ready Myotis: without two agreeing endpoints or a ready Myotis, every step that signs is `safe_unverified`, with Colibri or without. A default install has three built-in Gnosis endpoints (`k = 3, m = 2`), so the quorum stands whenever two of them answer.
- **Verified, or nothing is signed.** Every read a signing or an execution rests on must come back labelled `verified` by 0005's rules: a verifier's proof (Colibri on Gnosis), or a quorum of at least two distinct endpoints that agree (0005's m ≥ 2, deviations `singleton-quorum` and `endpoint-dedup`). These are the code at the Safe, the nonce, the singleton, the owners, the threshold, the guard, the modules and the handler. If any one of them isn't, `safe.prepare`, `safe.propose`, `safe.sign_owner`, `safe.execute`, `safe.message_start` and `safe.message_sign` fail with `safe_unverified`: "Freedom couldn't verify this Safe on Gnosis, so it won't sign. Try again, or add an RPC provider in Settings." Nothing is signed, and no `{ send }` is prepared (deviation `safe-unverified`). A read for display only, such as `safe.status`'s balance and cost, keeps its label and blocks nothing. `safe.status` signs and executes nothing, so it reports what the setup reads show as data for the board, its `setup` ([API](#api)), and never refuses with `safe_unverified`, `safe_changed` or `not_deployed`: those refuse only the steps listed here (decided 2026-11-27, Codex's round 1 on #527). It reads the code and the six setup reads, and no nonce, which it doesn't show.
- **Deployed:** a record is marked deployed only on verified evidence (decided 2026-11-26), as #1066's rule has it: a `verified` receipt with status 1 whose factory `ProxyCreation` log names the record's address, or a `verified` `eth_getCode` at the record's address that isn't empty. An unverified answer reports "deployed" for the session only, without writing it, so a later verified read or a deployment can still decide (deviation `deployed-mark`, F-4). Main's own path, `accounts.mark_safe_deployed` after its verified check, stays until SAFE-3.
- **A read that can't be used** (confirmed by SAFE-2's S1, #525), as the `safe_unverified` and `safe_changed` rules imply. `SafeL2` 1.4.1's four view functions never revert, and each answers in one encoding, so neither a reverted `eth_call` nor an answer `check_setup` can't read (its `ReadError`) can be evidence of the Safe's setup. Either is `safe_unverified`, with nothing signed, and the next attempt reads again. The exception is a Safe whose verified slot 0 isn't `SafeL2` 1.4.1: its calls answer for another contract, which `check_setup` doesn't compare, so the singleton alone decides, and the answer is `safe_changed`. A slot answer that can't be read is `safe_unverified` too.
- **Not deployed** (for S2 to S5, from what S0 found): the reference refuses to send, execute or sign a message for a Safe it hasn't marked deployed (`safe-transactions.js:296–297`, `471–472`; `safe-messages.js:339–340`: "Activate this account on Gnosis before sending", "… before signing for apps"). So `safe.prepare`, `safe.propose`, `safe.execute` and `safe.message_start` refuse a Safe the record doesn't mark deployed, before any read, with nothing signed; and a `check_setup` answer of `NotDeployed` (no code, verified) refuses every step that signs, `safe.sign_owner` and `safe.message_sign` included. The code is `data.safe: "not_deployed"` (confirmed by SAFE-2's S2).

### Owners, threshold and setup

Before each owner's signature and before execution, the core reads the [setup](#chain-reads), each read verified, and requires:
- the singleton is `SafeL2` 1.4.1;
- the owners, as a set, are the record's owners' addresses;
- the threshold is the record's;
- no guard, no module, and the canonical fallback handler.

Anything else the reads show is `safe_changed`: "This Safe was changed outside Freedom, so Freedom can't sign for it." Nothing is signed. The board shows the state, from `safe.status`'s `setup` (`changed`, naming what changed), and offers only to discard (deviation `safe-setup`). Today Freedom counts the record's owners and threshold and never reads the Safe's.

**As `fc-safe`'s `check_setup` does it:** the singleton is slot 0's whole word, `SafeL2`'s address with the high 12 bytes zero; the owners match as a set, in any order; no module is `getModulesPaginated(0x1, 1)` answering an empty page with the sentinel as `next`, since `enableModule` links a module at the head. It names every change it finds. Under another singleton the calls answer for that contract, so they aren't compared, and the change named is the singleton, with the guard and the handler if those changed too. A Safe with no code isn't deployed: it is reported so, not as changed, since its address commits to the record's setup, and the reference sends, executes and signs messages only for a Safe marked deployed. An answer that isn't Safe 1.4.1's encoding (a word that isn't 32 bytes, a list whose offset, count or length isn't Solidity's, an address word with its high bytes set) is a read error, never a change.

#### What the setup check can't see

Safe 1.4.1 accepts a signer when `owners[signer]` is nonzero and a module when `modules[module]` is, both mapping lookups, while `getOwners()` and `getModulesPaginated` walk the linked lists from the sentinel. A SafeTx executed outside Freedom with `operation` 1 can delegatecall code that writes a nonzero `owners[X]` or `modules[M]` without linking it, and without changing `ownerCount`. No read of this set can find such an entry, nor can any bounded set of reads, since its key is unknown. So `check_setup` answers `Unchanged`, and then X can sign for the Safe, or M can execute from it.

- **Who could do it:** the owners are the user's own accounts (Q24), so it takes the Safe's threshold of the user's own keys signing a delegatecall outside Freedom, for example after exporting a key to another wallet.
- **Freedom never writes one:** it builds every SafeTx as a CALL, and refuses a site's call to the Safe (question 4).
- **What the check guarantees:** the Safe's current setup, as these reads see it, is the record's. It says nothing of the Safe's history: owners added and removed again, or a threshold changed and restored, leave no trace in it. It doesn't rule out a hidden owner or module that a delegatecall wrote outside Freedom. That stays a known limit. Enforcing it needs a different defense, such as a guard Freedom installs at creation, and that is a design change.

**A site's transaction to the Safe itself** (`to` is the Safe: an owner, threshold, module, guard or handler change) is refused with `safe_self_call` ([question 4](#open-questions), decided 2026-11-25). `to` being the Safe catches every setup change: the Safe's setup functions accept only a call from the Safe itself, and Freedom builds every SafeTx as a CALL, never a delegatecall ([Built and hashed in the core](#built-and-hashed-in-the-core)). The wallet's own screens never build one.

### Owner signatures

- **One confirmation covers every local owner,** as today (0012): `safe.propose` spends the `safe-send` token and stores the SafeTx the token bound. `safe.sign_owner` signs only a pending SafeTx that was stored that way, and only for one of the record's owners. A SafeMessage's owners sign through `safe.message_sign` ([Messages](#messages-eip-1271)).
- **A vault owner** signs in the core at once while the vault is unlocked: at `safe.propose`, and when the board opens.
- **A Ledger owner** signs through the [device lane](#the-device-lane), when the user taps its row.
- **A phone owner** signs through 0012's phone job, once PHN-1 exists.
- **Every signature** is recovered over the SafeTx's hash, and must come from an owner in the record and in the Safe's set. Only 65-byte signatures with `v` 27 or 28 are kept: Freedom makes no other kind (deviation `owner-signatures`). Each also needs a low `s`, as every signature 0002 makes and `fc-evm` recovers; ethers refuses a high one too. A second one from the same owner is dropped.
- **The pending entry is checked again** when it is loaded: its hash must be the hash of its SafeTx fields for the record's Safe. An entry that doesn't recompute is set aside, and nothing signs it.

### The executor

- **The executor is a vault account,** the first vault owner, as today (`pickDefaultExecutor`). The core signs its transaction itself.
- **`safe.execute`** checks the setup and the nonce, builds the calldata from the pending SafeTx and its signatures, and prepares the executor's transaction: `to` the Safe, `value` 0, the gas estimate with 0012's 20% buffer, the fees from the core's quote. It runs 0005's fee check (0012's `fc-approval`). It answers `{ send }`, the transaction without its nonce, as `fc-eip1193` prepares a page's send (0012). Or `{ fee_check }`, for the Safe's screen to confirm the fee with an `executor-send` token, as today. Or `{ superseded }`.
- **Main** chooses the nonce under the executor's lock, has `sign.transaction` sign the prepared transaction with nothing else changed, journals it and broadcasts it, then tells the core with `safe.executed { safe, safe_tx_hash, hash }`. The core clears the pending entry, as today.
- **The nonce:** a Safe nonce past the SafeTx's is `superseded`, as today. One below it is refused with `safe_nonce_behind` (deviation `nonce-behind`: today the estimate fails with the node's text).
- **The deployment** goes the same way: `safe.deploy` → `{ send }` to the factory; main signs, journals and broadcasts; `safe.deployed { safe, hash }` after the receipt, and the core marks the record deployed only on [verified evidence](#chain-reads): the receipt verified, status 1, with the factory's `ProxyCreation` log naming the record's address, or a verified `eth_getCode` at it that isn't empty.

### Messages (EIP-1271)

- **`safe.message_start`** (page): the core checks the setup, builds the SafeMessage and its hash, spends the `safe-message` token or checks the standing rule as 0012 does, collects the vault owners' signatures, and opens a session bound to the page (`PageContext`) with a session ID of 16 random bytes in place of today's UUID.
- **The board's calls** name the session: `safe.message_sign`, `safe.message_state`, `safe.message_cancel`, and `safe.message_complete`, which returns the joined signatures once the threshold is met. `safe.message_sign { safe, session, owner? }` signs the session's SafeMessage for one owner (decided 2026-11-26), as `safe.sign_owner` signs a pending SafeTx: it reads the setup first, as before every owner's signature; a vault owner signs in the core, and a Ledger owner on the [device lane](#the-device-lane), under main's binding of the SafeMessage ([Main's typed-data binding](#mains-typed-data-binding)). Main cancels a session when its document goes, as `attachRequesterLifecycle` does today.
- **Sessions** stay in memory, one per Safe, as today.

### The pending store

- **`safe-pending.json` is the core's** since 0013's PRF-6(d) (the reference at `dea09d2f5`), in today's format, with 0001's atomic writes. A file that doesn't parse is renamed aside and reported, as 0012's files are (0013's `safe-pending-unreadable`; F-6, closed).
- **One pending SafeTx per Safe,** as today. Its `data` is at most 64 KiB (proposed), so the executor's calldata stays far below what transaction pools accept. The file is at most 1 MiB (decided 2026-11-26), the bound 0013 (*Bounds*), `fc-wallet-state`'s codec and `stores.json`'s `safe_pending` already pin: a write past it is refused with the store unchanged, and `safe.propose` answers `invalid_argument` with `data.safe: "store_full"`. A larger bound would make an older core, whose codec reads at most 1 MiB, rename the file aside.
- **`display`,** the chrome's text for the board and the payment record, stays as opaque display data. The board shows the core's view of the SafeTx beside it.

### protocol-kit out of main

After SAFE-3, main's `wallet/safe/` modules are thin clients of the core's `safe.*` methods. `@safe-global/protocol-kit` and `@safe-global/safe-deployments` leave `package.json`, and `@safe-global/types-kit` and `@safe-global/safe-modules-deployments` leave the lockfile with them. `viem` stays, since `@x402/evm` needs it. `stub-chain.js` is retired. The Safe e2e suites keep passing.

## Approvals: enforced

0012 lists a Ledger's signatures, a Safe's Ledger owner's included, as advised until this design, and enforces a Safe's vault owners' and executor's from APR-4, through Safe approvals. From LDG-2 a Ledger's are enforced too, and from SAFE-2 a Safe's tokens bind the SafeTx the core built, under 0012's rules: checked when present at first (APR-3's rule), and required once APR-4's rule applies.
- **A Ledger account** is treated as a vault account is. A page's signature needs a token or a standing rule the core checked for that page; a `chrome` call needs a wallet-kind token; a `shell` call carries none. A standing rule skips the browser's prompt, never the device's. For x402, `x402.authorize` (X402-1) takes main's `now_s` for a Ledger account and returns its authorization as typed data, which main rebuilds, compares and sends back as `x402.settle { reservation, typed_data }`, which the core signs on the device lane ([x402 from a Ledger account](#x402-from-a-ledger-account)).
- **`safe-send`** binds the SafeTx the core built at `safe.prepare`, in a new form, `{ safe, chain_id, safe_tx, safe_tx_hash }`: the Safe's address, the chain, all ten fields (the nonce included) and its hash, and, for a site's, the page and the handle (0012). Only `safe.propose` spends it.
- **The legacy `safe-send`,** `{ safe, chain_id, tx: { to, value, data } }` (0012's, `fc-approval`'s `Approved::Send`), keeps APR-4's path until SAFE-3 (decided 2026-11-26): `approval.spend` gives its Safe approval, for the SafeTx main builds itself, as today. Neither form is spent as the other.
- **Owner signatures** need no token each: the spent `safe-send` authorized every local owner's signature over that SafeTx, as today.
- **The executor's transaction** is signed only as `safe.execute` or `safe.deploy` prepared it, or with an `executor-send` token for a fee the check stopped.
- **`safe-message`** binds the method, a digest of the request, the digest the SafeMessage carries and the SafeMessage's hash, the page and the handle. `safe.message_start` spends it.
- **0012's table** loses its "advised until 0016" row, a Ledger's ([Amendments](#amendments)).

## Options weighed

- **HID in the core** (hidapi): a C dependency and per-OS device code in the core, and a device grant for D7. In Stage 1 it protects against nothing the core's checks don't, and mobile needs another transport anyway.
- **A Ledger service process:** the parser surface is a few fixed-size answers; a process would isolate very little.
- **Main relaying HID reports, not APDUs:** main couldn't check anything, and the framing would move into the core for no gain.
- **hw-app-eth kept in main, with the core checking the result:** main would still choose the bytes, and F-2 would stay.
- **Approval records on disk:** they would survive a restart, but an older build never sees them, so it can't remove one when it discards the SafeTx, and a removal that fails on disk leaves one behind. Making that safe needs set A's whole contract plus a marker every older build honors. In memory, a record never outlives its process, for one more approval after a restart.
- **x402 through `sign.typed_data`** (this design as first written): `sign.typed_data` with the Ledger key and a new `authorization: { x402 }`, then `x402.settle`. That takes two calls, and under `shell` the binding holds only if main presents it. `x402.settle { reservation, typed_data }` binds it structurally, and its refund path already exists.
- **x402 as #392 builds it** for a Ledger: the time bytes stay the core's, against the threat table's x402 row.
- **Refusing Permit2 on a Ledger:** simpler, but Ledger users pay with Permit2 today, and the rebuild is one fixed row of a table.
- **Refusing the hash-only fallback** (Q23's proposal, not taken): the device would always show what it signs, but a Nano S couldn't sign typed data in Freedom: permits, x402 payments, sign-in requests that use typed data, and a Safe owner's SafeTx and SafeMessage. The user kept the fallback, with its warning.
- **protocol-kit kept in main, with the core checking its SafeTx:** the address, the deployment and the reads would stay protocol-kit's, which is where F-4 is.
- **Safes made elsewhere, or other versions and chains:** each needs its own deployments, its own setup rules and a way to show them. Q24 keeps them out until a design adds them.

## Open questions

1. **Q23, Ledger typed data:** Should Freedom refuse to sign typed data on a Ledger that can't show its fields (the Nano S shows only two hashes), so you always see what you sign, even though a Nano S then can't sign permits, x402 payments or Safe transactions in Freedom? *Proposed: yes.* **Decided 2026-11-24: no, the hash-only fallback stays,** despite its risk: only after the device answers `6D00` to the operation's first `E0 1A`, with `fc-evm`'s hashes of the bound typed data, and with a warning, on screen before the device asks, that the device shows only hashes ([Typed data on the device](#typed-data-on-the-device-q23)).
2. **Q24, Safe:** Should Freedom support only the Safes it creates today (Safe 1.4.1 on Gnosis), and refuse to sign for one whose owners, threshold or setup were changed elsewhere? *Proposed: yes.* **Decided 2026-11-24: as proposed,** the setup checked by verified reads before every signature ([Which Safes](#which-safes-q24)). Noted 2026-11-26: the reads see the current linked setup, not an owner or module a delegatecall wrote outside Freedom ([what the setup check can't see](#what-the-setup-check-cant-see)).
3. **A new Ledger account:** When you add a Ledger account, should the Ledger show its address for you to confirm there? *Proposed: yes.* **Decided 2026-11-25: as proposed** (`E0 02 01 00` under `ledger.add`, [Accounts](#accounts)).
4. **Safe self-changes:** Should Freedom refuse a site's Safe transaction that would change the Safe itself (its owners, threshold, modules, guard or fallback handler), which Freedom can neither show nor follow? *Proposed: yes.* **Decided 2026-11-25: as proposed:** a site's Safe transaction whose `to` is the Safe is refused with `safe_self_call`. The Safe's setup functions accept only a call from the Safe itself, and Freedom's SafeTx is always a CALL, so that catches every setup change ([Owners, threshold and setup](#owners-threshold-and-setup)).
5. **Waiting for the Ledger:** When a Ledger request waits behind another one on the device, should that wait count against the 5 minutes you have to confirm it? *As written* ([The device lane](#the-device-lane)): yes, so a signature that waited 4 minutes in line has 1 minute left to confirm on the device. *Proposed* (the coordinator's recommendation, 2026-11-26): no. The wait in line is capped on its own at 5 minutes, and every confirmation gets its full 5 minutes on the device, so a request can take up to 10 minutes in all. *Open: the user's to decide.* Either answer keeps each APDU's `deadline_ms` as [`shell.ledger_apdu`](#shellledger_apdu) has it; the answer decides only how the lane bounds a wait in line.
